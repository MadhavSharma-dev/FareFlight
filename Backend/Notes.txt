FareFlight is a microservices-based flight booking system designed to handle high-concurrency scenarios like multiple users trying to book the same seat simultaneously 

The system starts at the client layer (web/mobile), routes traffic through a CDN for static assets and a Load Balancer for API traffic, hitting an API Gateway that handles authentication and routing to three core microservices — Auth, Search, and Booking.

Search Service flights fetch karta hai aur unhe rank karta hai dynamic pricing ke saath, jo Pricing Engine se aati hai. Jab user koi seat select karta hai, tab Booking Service ek Redis-based seat lock lagate hai (SETNX) taaki do log ek hi seat book na kar sakein — isse double booking rokti hai.

Uske baad payment charge hoti hai — agar payment successful ho gayi toh seat confirm ho jaati hai, aur agar payment fail ho gayi toh lock release ho jaata hai aur ek Seat Released Event Kafka pe publish hota hai. Yeh event downstream consumers ko trigger karta hai jaise Payment, Notifications (Email/SMS), Waitlist processing, aur Search Reindexing.

Data layer mein Postgres write DB hai, aur Read Replica scale karne ke liye use hoti hai. Fast reads ke liye Cache hai aur flight queries ke liye Search Index. Observability ke liye logs, metrics aur tracing sabhi services mein cover ki gayi hai.

LLD Breakdown : 

Search & Selection: A user searches for tickets, and the system returns filtered, ranked, and dynamically priced results before the user selects a seat to book.

Seat Locking: The system attempts to temporarily lock the seat (using Redis SETNX and DB version checks) to prevent double-booking. If it cannot lock the seat, it returns a 409 error.

Payment: If the seat is successfully locked, the system proceeds to charge the payment.

Final Outcome: If payment succeeds, the seat is confirmed; if payment fails, the seat is released via a system event so others can book it.


User flight search karta hai → results filter, rank aur dynamic price ke saath aate hain.

User seat select karta hai → Redis SETNX se seat lock acquire hoti hai. Agar lock nahi mili → 409 error. Agar lock mil gayi → payment charge hoti hai.

Payment success → seat confirm. Payment fail → seat release ho jaati hai aur Seat Released Event Kafka pe jaata hai.

Why CDN and Load Balancer separately?

A CDN is a network of servers spread across the world that stores copies of your content (images, videos, CSS, JavaScript, sometimes whole pages) close to your users. When someone in Delhi requests your site, they get files from a nearby CDN server instead of your origin server in, say, Virginia.

Load Balancer helps in distrubuting the traffic among different servers

Basicslly TTL is a part of caching that gives you some time to perform that task and if the task is not performed within that particular period then Redis automatically deletes it from cache memory
